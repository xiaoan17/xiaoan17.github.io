拆开 Qoder CN 0.4.11：Electron 工作台、Claude Code 血统的运行时与十五个逻辑模型

✍️ 安博成 · 📅 2026-10-25 · 🏷️ AI Agent, Qoder, 技术拆解, 架构

Qoder 是我最近用得最多的一个桌面 Agent。它的产品页讲的是「Agent workbench for human and AI software teams」，但真正有意思的东西都藏在安装包里：一个 176 MB 的 app.asar、一个 33 MB 的混淆 Agent 运行时、一张 110 张表的 SQLite、十个自带扩展，以及一个能锁屏后继续替你点鼠标的独立 helper app。

于是我把本机这版 macOS 客户端拆了一遍。和上一篇拆 DuMate 的方法一样：只看安装包结构、配置、二进制符号、数据库 schema 和运行日志里的请求元数据。

边界

只读分析，没有绕过鉴权，没有展开任何对话内容。会话正文、消息、附件一律没读；日志只看请求行、模型代号、耗时和状态码。结论只代表这个版本、这个平台、这个账号。

TL;DR

Qoder CN 是「Electron 壳 + React 工作台 + Claude Code 血统的 Agent 运行时 + SQLite 化的本地控制面 + 十五个逻辑模型键」。

模型侧最重要的设计不是用了哪家模型，而是客户端根本不写死模型：目录里只有 qfmodel、kmodel_latest、qmodel_38max 这类代号，真名由网关目录下发。本次观测到 qfmodel → Qwen3.8-Flash、kmodel_latest → Kimi-K3.1-Pro，两者都是 180K 上下文、多模态、model 字段留空等网关改派。

运行时侧最重要的发现是血统：工具名、SKILL.md、hooks、agents、chat.proto 的字段设计，和 Claude Code 那一套高度同构。Qoder 没有从零造一个 Agent OS，而是把一套成熟 harness 重写成自己的 worker，再把差异化放在「手」和「端」上——电脑操控、手机操控、站点托管、遥控、Agent Team。

一、探测对象与方法

本地数据库main.sqlite 9.5 MB，110 张表 / 202 个索引

方法：

  • 用 asar 头部解析 app.asar 的文件表，按需抽取主进程、渲染层与 SDK 文件；
  • 用 strings / 正则扫随包二进制与混淆 bundle，找工具名、端点、模型键；
  • 读 ~/Library/Application Support/com.qodercn.app.stable/*.sqlite 的 schema 与行数（不读 payload）；
  • 读 ~/.qoder-cn/logs/runs/*/qodercli.log 的请求行、模型代号与耗时；
  • 看进程树、监听端口、TCC 声明、签名主体；
  • 对照官方文档与扩展包内的 manifest。

从外到内五层：

  1. 渲染层：React 19 工作台，负责会话、工作区、站点、自动化、扩展市场、浏览器标签页。
  2. 本地控制面：Electron 主进程，把会话、协作、遥控、市场、自动化、额度都收进本地 SQLite，并暴露一个 MCP router。
  3. Agent 运行时：被主进程拉起的 qoder-worker-runtime，管 agent loop、工具、hook、技能、子代理、记忆。
  4. 执行器：本地 shell、代码检索索引、电脑操控 helper、手机操控（Appium）、站点服务。
  5. 云服务：模型网关、模型目录、代码库同步、站点托管、额度与遥控信令。

跟 DuMate 的「Go 控制面 + OpenCode 运行时」相比，Qoder 少了独立控制面二进制，多了「控制面直接长在 Electron 主进程里」；多出来的是插件市场、站点托管、遥控和 Agent Team。

三、桌面壳：不是聊天框，是工作台

打开就是那张「不止于编程」的首页。它的信息架构已经说明定位：左边是「新的任务 / 工作区 / 最近任务」，下面四个入口是「站点 / 自动化 / 扩展 / 更多」，输入框上还有「手机遥控电脑」。会话只是六分之一。

几个可验证的细节：

  • 前端用 React 19 + @qoder-space/workbench、editor-core、design-system、artifact-preview、collaboration-core，外加 xterm 6、Shiki、framer-motion、gsap。这是一个 IDE 级工作台，不是聊天页。
  • chat_sessions 表里两个维度很能说明问题：product_mode 取 coding / general（对应界面左上角的终端图标与「通用」），conversation_mode 取 normal / voice。本机 73 个会话里 70 个是 general。
  • 主进程会用自己的可执行文件再拉起运行时（argv 里带 --sdk），进程环境里有 QODER_CONFIG_DIR=~/.qoder-cn： 
    Qoder CN .../qoder-worker-runtime.obf.mjs --sdk
    也就是说，744 MB 的壳同时兼任 JS 宿主，不必额外塞一个 node 运行时。
  • 原生能力散在 Contents/Frameworks 和 Contents/Resources/bin：node-pty（终端）、sharp（图像）、keytar（钥匙串）、native_clipboard、notification_permission、hosted_presentation_host（共享演示）、dji_mic_button（大疆麦克风的硬件按键）、appshot_bare_modifier_monitor（组合键截屏监听）。

混淆边界值得单独说：主进程、preload、worker 全部混淆（字符串表 + 解码器），但 extensions/、plugins/、computer-control 这些扩展的 JS 完全没有混淆，还保留着 // src/node/main.ts 的源码路径和中文注释。这是一个很清楚的取舍：核心链路防逆向，能力层要可读、可调试、可审计。

五、Agent 运行时：一套被重写的 harness

qoder-worker-runtime.obf.mjs 33 MB，混淆但没加壳。runtime-info.json 里泄露了不少构建信息：版本 1.1.75-hotfix.1、commit cb3c036、profile: "platform"、buildEnv: "dev"，以及一条 Aone CI 的绝对路径（aoneci-runner/.../dist-worker-runtime-cn）。随包带 sharp、photon、keytar、node-pty 和 vendored 的 ripgrep。

工具表是从常量区直接读出来的，42 个名字，去掉 3 个 PTY 事件（BashInput/BashOutput/BashResize）和 3 个重复别名，实际注册面约 36 个：

这份表比任何产品文档都诚实：Agent + SendMessage 意味着子代理与 Agent 间通信，Cron* + ScheduleWakeup 意味着「自动化」不是外挂而是运行时原语，ImageGen/VideoGen 说明它不止写代码，CodebaseInvestigator 说明代码库理解是一个独立工具而不是塞进 grep。

权限模型有三种，日志里都能看到：default、auto、bypassPermissions（界面上叫「自动审批」）。auto 不是简单地全放行，而是走一层分类器：

[permission-check] main Bash mode=auto → allow point=shell.readonly.allow
[permission-check] main Bash mode=auto → allow point=mode.auto_classifier.allow
[permission-check] main Bash mode=auto → deny  point=mode.auto_classifier_blocked.deny

只读命令走白名单，其他命令问分类器，分类器说不就拒。

协议层也留在包里：proto/chat.proto（322 行，protobuf）。请求体是 OpenAI 兼容的 chat completion，但加了几样东西——patches（逐轮补丁）、cache_id + cache_control（提示缓存）、ReasoningEffort（NONE/LOW/MEDIUM/HIGH/XHIGH/MAX）、ReasoningItem.encrypted_content、custom_model。这说明上下文不是每次全量重发，而是「缓存 + 补丁」的增量模型。

记忆与自进化：

  • memory/ 三件套 MEMORY.md、SOUL.md、IDENTITY.md，和 Claude Code 的约定同构；远端配置里有个开关 auto_memory_policy { extractionEveryNTurns: 5 }，即每五轮抽一次记忆。
  • skill_evolution_suggestions 有完整生命周期：pending → starting → evolving → evolved / dismissed / expired / hash_invalidated，带置信度和 evolution_session_id。也就是说它会另起一个会话把「这次的经验」写成技能文件，再用文件哈希防冲突。

六、模型层：十五个逻辑键，目录加密

这是我最关心的部分，也是最像「工程决策」的部分。

chat_model_preferences 里有 15 个产品目录键（都 visible=1）：

auto  fast  gmodel  gfmodel  gm51model  dmodel  dfmodel  mmodel
kmodel  kmodel_latest  qmodel  qmodel_latest  qmodel_38max  q37fmodel  qfmodel

命名规律几乎写在脸上：q* = Qwen、k* = Kimi、g* = Gemini、d* = DeepSeek、m* = MiniMax，fast 是轻量档，auto 是路由。*_latest 追最新，固定名（如 qmodel_38max）钉版本。

从日志里抓到的真实映射只有两条，但足够说明机制：

表格较宽，移动端可左右滑动 →

逻辑键展示名is_vl上下文model 字段
qfmodelQwen3.8-Flashtrue180,000空
kmodel_latestKimi-K3.1-Protrue180,000空

model: "" 是关键：客户端只知道「我要 qfmodel」，真实后端型号由网关决定。这和 DuMate 的 model-text / X-Dumate-Gw-Realmodel 是同一套思路，区别在于 Qoder 没有把真实型号回显给用户——日志里没有 header，界面上也只有展示名。

目录本身是加密的：~/.qoder-cn/.models/<uid>/catalog-v6|v7 是 base64 文本，解码后开头是 QMC magic，后面的内容解不开。客户端每启动会拉 /api/v2/model/list（本次窗口 225 次），所以换模型、加档位、灰度都是服务端的事。

BYOK 是一等公民：settings.json 里的 providers.* 可以挂任意 OpenAI 兼容端点，byok_model_profiles 表记录 endpoint_url、protocol_style、is_vision、is_reasoning、efforts_json。本机就挂了一个本地网关（62 个模型），传输标记是 custom-openai，而产品自带链路标记是 legacy（SSE）。

后端痕迹：包里同时存在两套 API 形状——Qoder 自己的 /api/v2/service/pro/sse/agent_chat_generation，以及 DashScope 风格的 /api/v2/service/pro/invoke/chat_like、generateImage、videos、/api/v1/services/aigc/multimodal-generation/generation；embedding 用的是 text-embedding-v3/v4；扩展市场包放在 *.oss-accelerate.aliyuncs.com；computer-use helper 的签名主体是「Hangzhou Yundian Technology Company Limited」。拼起来，云侧大概率是阿里云百炼 + OSS 这条线。

七、「手」和「眼」：四个执行器

Agent 的差距常常不在模型，而在能不能真的动手。Qoder 这块投得很重，而且是四个独立的进程/包：

1. 代码检索（qoder-search）。5.4 MB 压缩 bundle，通过 MCP 暴露 SearchKnowledge、SearchCodebase、SearchWiki、ReadWiki、ReadModuleKnowledge。本地带 rg（4.5 MB）和一个自研原生模块 mtree（1.7 MB）——从 /codebase/sync/{getMerkleNode,batchGetMerkleNodes,updateMerkleNodes} 这组端点看，是 Merkle 树式的增量同步；embedding / rerank / chunk 检索走远端 /api/v2/service/codebase/*。顺带纠正一个常见猜测：bundle 里 trigram、bm25、FTS5 计数全为 0，本地并没有 BM25 倒排。

2. 电脑操控（computer-use）。不是主进程里的一个模块，而是一个独立签名的 app：com.qoder.cn.computeruse 2.2.13，LSUIElement（无 Dock 图标），已公证。里面还有 Bridge、LockScreenGuardian 和一套 LockedUse 安装器 + 授权插件。协议是 unix socket、单帧上限 1 MiB、初始化超时 5 秒。它的 entitlements 只有一条 com.apple.security.automation.apple-events，Info.plist 里也只声明了 Apple Events 用途串——辅助功能和屏幕录制走运行时 TCC，不在清单里写。LockedUse 的语义从配置文案能看出来：接管期间锁屏，键盘或点击会重新锁定。

3. 手机操控（phone-use）。84.7 MB，4,085 个文件，带 @appium/*、appium-ios-device、scrcpy-server.jar。MCP mobile 暴露 39 个工具：Android 11 个（android_connect/observe/tap/type_text/open_app/batch…），iOS 28 个（ios_connect/observe/install_runner/check_signing/provision_signing…）。这是把移动端自动化真做进了客户端，而不是发个链接让用户自己点。

4. 站点（sites）。22 个工具，覆盖 publish_site、update_access_policy、create_database_migration、update_database_row、get_function_logs、get_analytics。首页那个「站点」入口后面是一整套「建站 + 数据库 + 函数 + 访问控制 + 分析」的托管面。

另外还有：canvas（内嵌 esbuild-wasm 14 MB，跑 .canvas.tsx）、office（pptx 预览器，带 harfbuzz wasm）、knowledge.center（qoder-qmind + repowiki 两个 MCP，19 个工具）。语音侧有 /api/v2/service/ws/asr 和实时语音会话，硬件侧甚至接了大疆麦克风的按键。

八、遥控与协作：十五张 rc_* 表

首页那个「手机遥控电脑」不是投屏，是一条完整的会话通道：

  • 信令：/api/v1/remote/qoder/remote-control/enable、/status，会话侧 /api/v1/remote/code/sessions；请求头带 X-Qoder-Remote-Protocol-Version、X-Qoder-Remote-Device-Identity-Version、X-Qoder-Remote-Api-Version。
  • 载荷：remoteControlProcess.js 会以只读方式打开会话库，把一轮轮事件整理成带 anchor、fact、events、offset、len 的增量流写盘，单帧上限 32 MB，路径必须落在会话目录内。这是「可续传的事件日志」，不是「把整段对话发过去」。
  • 状态：rc_ingress_environments/bindings/inbox/deliveries/timeline/management 管入口与投递，rc_history_sync + rc_history_body_proofs 管历史对齐与正文校验，rc_identity_migrations + rc_scope_continuity 管身份与作用域续接。十五张表拼起来，是一条「准入 → 同步 → 续接」的链路。

协作侧则是另一套：discussion_*、collaboration_*、issue_agent_*，加上 agent_teams（leader_server_agent_id、invocation_policy）和 agent_registration_outbox（本地 Agent 注册到云端的发件箱）。产品上叫「Agent / Team / 讨论」，实现上是「本地实体 + 云端注册 + 消息投递」。

九、一次任务的旅程

User → React workbench → 主进程（IPC）
  ├─ 写 chat_sessions / turn 状态
  ├─ 组装上下文：qoder-search（rg + mtree + 向量）
  └─ spawn worker（--sdk）
       ↓
  agent loop（~36 工具 + hooks + skills）
       ↓
  本地执行：shell(node-pty) / 文件 / 电脑操控 / 手机 / 站点
       ↓
  推理：gateway.qoder.com.cn（逻辑键 → 网关改派 → SSE）
       ↓
  落库：messages / turn_file_change_* / FTS / 记忆 / 技能演化建议
  1. 用户输入 → 渲染层 → 主进程，先落一条 chat_sessions，再按 product_mode 选系统提示词。
  2. 检索层用 rg + mtree 算增量，向量检索走 /codebase/search/retrieveChunks。
  3. worker 起 agent loop，按 default/auto/bypass 三档过权限，auto 走分类器。
  4. 推理请求带逻辑键和 reasoning effort，走 SSE；auto 由目录策略挑一个 *model。
  5. 工具落到本地 shell、computer-use、phone-use 或 sites。
  6. 每轮结束写 turn_file_change_sets/patches，同步 FTS，按 extractionEveryNTurns=5 抽记忆。
  7. 会话结束（或用户确认）后，可能生成一条 skill_evolution_suggestions，由独立会话把经验写成技能。

差异化端云协同、BOS、企业 BYOM站点托管、自动化、遥控、Agent Team、技能自进化

有意思的是两家在模型层做了同一个决定（逻辑模型与真实后端解耦），却在可观测性上分道扬镳：DuMate 用 X-Dumate-Gw-Realmodel 把头回显给客户端，Qoder 选择不暴露。前者利于排障和用户沟通，后者利于统一体验和商业灵活度——这是个产品选择，不是技术优劣。

十一、设计取舍：Qoder 做对了什么

  1. 把「工作台」当第一性，而不是把「对话」当第一性。 会话、站点、自动化、扩展、浏览器是并列的面，product_mode 只有 coding/general 两档，说明它默认用户是来「做事」的。
  2. 模型层抽象得彻底。 十五个逻辑键、model 字段留空、目录服务端下发、BYOK 一等公民——换供应商、加档位、灰度、企业自带模型，全是配置问题。
  3. 复用成熟 harness，把创新压在「手」上。 工具命名、SKILL.md、hooks、agents、chat.proto 都能看到 Claude Code 的影子。这不是偷懒，是把最不容易差异化、也最容易踩坑的部分标准化，然后把预算投到电脑操控、手机操控、站点托管这些真差异点。
  4. 本地控制面 SQLite 化。 110 张表把会话、遥控、协作、市场、自进化全收在本地：离线可用、可迁移、可审计，也让「历史任务」不依赖云端。
  5. 插件双层设计。 宿主侧 .qoder-app-plugin（views/services/permissions）和 Agent 侧 .qoder-plugin（skills/mcpServers/commands）分离；十个内置扩展 144 MB，等于自带一套「Office + Canvas + 站点 + 手机 + 知识库」。
  6. 混淆划了边界。 核心链路混淆，扩展层完全不混淆。这既保护了推理与调度逻辑，又让能力层可读、可调试、可被第三方照着写。

如果要挑毛病，最明显的是可观测性：日志不落任何 header，模型代号到真实后端的映射只在服务端，catalog-v6/v7 还是加密的。用户看到「Kimi-K3.1-Pro 高」，但没有任何办法确认这一次到底跑在谁身上。

十二、未解的问题

  • 十五个逻辑键里只观测到两个真实映射（qfmodel、kmodel_latest）；gmodel/mmodel/dmodel 是按命名推断的，没有实跑证据。
  • auto 的路由策略没抓到：是打分、是规则、还是 LLM 决策，日志里只有结果没有依据。
  • 模型级 fallback 没观测到，只看到端点级的地址 failover（contractMaxAttempts=3、contractAddressFailover=true）。
  • catalog-v6/v7 是 QMC 开头的密文，解不开；目录的真实结构未知。
  • 遥控协议的帧格式只从落盘逻辑反推，端到端没抓包。
  • auto_classifier 用什么模型、什么提示词判定「这条命令能不能跑」，没有证据。
  • 样本只有 macOS arm64、单账号、十天窗口；Windows 端和 Linux 端的执行器差异未覆盖。
