拆开百度搭子 DuMate v1.0.88：Electron 壳、OpenCode 心与多模型网关

✍️ 安博成 · 📅 2026-10-25 · 🏷️ AI Agent, DuMate, 技术拆解, 架构

百度搭子 DuMate 是 2026 年讨论度很高的国产通用 Agent 之一。它强调「真干活」：跨应用、跨文件、操作浏览器、直接交付文档和网页。产品页写得很满，技术细节却很少。于是 10 月 25 日，我把本机安装的 macOS 版 v1.0.88 拆了一遍。

先说明边界：这是只读分析，没有绕过鉴权，也没有展开任何用户对话内容。我看的是安装包结构、配置文件、二进制符号，以及运行日志里的请求元数据和响应头。结论只代表这个版本、这个平台。

TL;DR

DuMate 是「Electron 壳 + Go 本地控制面 + OpenCode 定制运行时 + 本地/云端双执行环境 + 多模型网关」。模型侧最重要的设计是逻辑模型 ID 与真实后端解耦：客户端写 glm-5，官方预置展示 GLM-5.2；L0 实跑却是 DeepSeek-V4.1-Flash，路由和摘要用 Qwen3.5-35B-A3B。

一、探测对象与方法

客户端版本v1.0.88（构建于 2026-10-24）
平台macOS arm64
桌面壳Electron 43.1.1
安装包DMG 591 MB；安装后约 1.0 GB
app.asar约 101 MB
移动端原生 Android（Kotlin/Compose），DumateMobile/1.20.0.10

方法很朴素：

  • 用 @electron/asar 解开 app.asar，看主进程与前端产物；
  • 用 strings 扫随包二进制，找模块名、模型 ID、路由常量；
  • 读 config/ 与运行数据目录里的 JSON、SQLite schema；
  • 读 log/desktop-main/Gateway.log 的请求行与响应头；
  • 对照官方文档、模型管理页截图和公开报道。
边界

只观察到一个 L0 会话；L1/L2（Turbo/Ultra）没有实测。只覆盖 macOS arm64，Windows 端可能有差异。端口、内部 hostname、模型别名都可能随版本变化。

从外到内可以分成五层：

  1. 渲染层：Electron + React，负责界面与交互。
  2. 本地控制面：Go/Gin，负责会话、项目、技能、模型注册、配额、文件、遥测。
  3. Agent Runtime：OpenCode 定制版，负责 agent loop、工具、技能、子代理、记忆。
  4. 执行环境：轻沙箱、VM、电脑操作、内置浏览器。
  5. 云服务：模型网关、千帆、BOS、企业 API。

这五层里，最容易被忽略的是第二层。大多数桌面 AI 产品只有一个壳加一个云 API；DuMate 在本地放了一个完整的控制面。

三、桌面壳：不是 WebView 套壳

第一个反直觉的点是：它没有用系统 WebView 套一个网页，而是完整的 Electron 43.1.1 + React。安装包里能看到 Electron Framework、四个 Helper、Squirrel 更新器，以及 app.asar 里约 101 MB 的前端与主进程代码。

还有四个原生 Node 插件：cookie_crypto、desktop_native、device_info、macos_notification_status。它们分别处理 Cookie 加密、桌面能力、设备信息和 macOS 通知状态。

用 Electron 的代价是包大、内存高；收益是跨平台一致、桌面集成能力强，且可以直接复用 Node 生态。对一个要操作本地文件、浏览器、系统通知的 Agent 来说，这笔账是划算的。

但渲染层不直接连云端。Agent 请求先到本地 Go 服务——这是它与「网页套壳」最大的区别。

四、本地控制面：一个装在桌面上的 Go 服务

dumate-main-server 是 57 MB 的 Go 二进制，配置里明确写着 gin_mode: release。从符号表能看出它的模块划分：

模块作用
apis/service本地 HTTP API
clients/opencode调用 Agent Runtime
scheduler定时任务
modelregistry模型注册与选择
skill / plugin / connector能力生态
filemanage / clients/bos文件与产物
tracking / otelrelay遥测与 OpenTelemetry
remotecontrol / deskhub远程控制与多端
security / relaycred安全与凭证

它把会话、项目、技能、插件、模型、配额、文件、遥测都收在自己这里。本地还有 SQLite：opencode.db（会话/消息）、desktop.db（文件任务）、memory.db（记忆）。

一次运行里观察到的本地端口：52701（控制面）、52609（OpenCode）、52036（Router）、19228（浏览器中继）。端口是动态的，不必记。

这也意味着历史任务、技能管理这类操作不必每次依赖云端。

五、Agent Runtime：OpenCode 定制版

dumate-opencode 约 104 MB，Bun 编译，配置直接使用 https://opencode.ai/config.json 作为 schema。默认 provider 配置是这样的：

{
  "model": "QianfanPersonalQuota/glm-5",
  "provider": {
    "QianfanPersonalQuota": {
      "npm": "@ai-sdk/openai-compatible",
      "options": {
        "baseURL": "http://127.0.0.1:52701/api/qianfanproxy/v1",
        "apiKey": "nokey"
      },
      "models": {
        "glm-5": {
          "id": "model-text",
          "limit": { "context": 192000, "output": 128000 }
        }
      }
    }
  }
}

注意两个细节：apiKey 是 nokey，因为真正的鉴权在本地代理；glm-5 的 id 是 model-text，说明客户端用的是逻辑别名，不是真实模型名。

运行时实际注册了 28 个工具，按用途可以分成九类：

类别工具
文件/命令bash、read、write、edit、glob、grep
网络webfetch、websearch
规划todowrite、todoread、phase-change、requirementread
多代理task
记忆memory_load、memory_search、memory_write
能力skill、plugin
调度scheduler_action、scheduler_create_job
交付file_export、file_download、mount_directory
其他get_location、extension-sync、question、date_calc

这 28 个工具是运行时实际注册的，不是文档里的愿景。task 意味着子代理，skill/plugin 意味着能力包，memory_* 意味着长期记忆。

本机 data/plugins/official/ 下有 5 个官方套件：设计、教育、金融投资、求职、自媒体。插件格式是 .claude-plugin/plugin.json + skills/<name>/SKILL.md——和 Claude Code 的约定高度兼容。再加上 MCP Server、连接器，能力生态就搭起来了。

记忆层也值得单独说：memory.db 是 SQLite，带 FTS5 trigram 索引；另有 MEMORY.md、USER.md、SOUL.md 三个文本层。记忆不是简单塞进 context，而是分块、检索、提升（promote）。

所以更准确的说法是：DuMate 的运行时是一个 Agent OS，而不是一个聊天客户端。

六、路由层：先决定「谁来干」，再决定「用哪个模型」

DuMate 的请求先经过一层任务路由，再经过一层模型路由。路由维度至少有五个：

维度取值含义
task_typedumate / ai_assistant主 Agent 还是轻助手
model_typetext / multimodal纯文本还是多模态
platformdesktop / cloud本地还是云端执行
featurephoto_solve 等特定功能路由
reasonsession_sticky、fixed_model_selected、deep_think_rule、attachment_rule、skill_rule、plugin_rule、llm_decision为什么这么选

决策顺序是：本地规则 → 远端 routing/decide（默认 3 秒超时）→ 本地 LLM 路由兜底。远端服务在代码里的默认地址是 http://dumate-meta-harness:8080/routing/decide；兜底模型是千帆上的 qwen3.5-35b-a3b。

模型档位内部是 L0 / L1 / L2，请求头带 X-Dumate-AutoModel-Level、X-Dumate-AutoModel-Target、X-Dumate-Model-Target。网关响应头会回传 X-Dumate-Gw-Realmodel 和 X-Dumate-Gw-Realmodel-DisplayName。

这套设计最妙的地方是可观测：自动模式下，客户端会把真实模型回写到消息里。用户能看到「这次到底用了谁」，而不是只看到一个模糊的「智能模式」。

七、执行环境：把「手」和「眼」也做进客户端

Agent 的差距，很多时候不在模型，而在「手」和「眼」。DuMate 在这块投入很重：

  • 轻沙箱：Python/Node 运行时分层，requirements.txt 锁定了 python-docx、python-pptx、openpyxl、pandas、PyMuPDF、reportlab、typst 等办公/文档依赖；Node 包单独一层。按需安装，不随版本全量重下。
  • 完整 VM：dumate-vm-manager + 约 47 MB 的 seed.iso.zst，用于更重的隔离执行。
  • 电脑操作：cu 是 Python 3.9 打包的二进制，链接了 AppKit、Quartz、ScreenCaptureKit，能截屏和做 GUI 自动化。
  • 浏览器：内置浏览器（IAB）通过 CDP relay，dumate-browser-extension-relay 监听本地端口；也支持 Chrome/Edge 扩展接管，带权限模式。
  • 文件：mount_directory 挂载工作区，file_export/file_download 导出，产物可上传 BOS 并注册 artifact。

这些能力让它可以真的改本地文件、点本地软件，而不是只给建议。代价是安全边界更复杂：目录权限、危险操作二次确认、沙箱/VM 隔离、审计日志，一个都不能少。

八、模型矩阵：一个入口，四家后端

这是我最关心的部分。把配置、文档截图和网关日志拼在一起，能得到这样一张表：

表格较宽，移动端可左右滑动 →

角色逻辑 ID真实后端证据

官方预置两条，来自企业版模型管理页截图：GLM-5.2（model-text，「超长无损上下文，长程工程任务强」）和 Kimi-K2.6（model-mm，「原生多模态，多模态理解能力强」）。客户端配置键仍写作 glm-5。截图里表格还能滚动，所以不能排除下面还有别的条目。

但日志里，model-text 的标题生成请求返回的是 deepseek-v4.1-flash-low-latency；model-reason-summary 返回的是 n2p5sdmw_qwen35-35b-a3b。这说明逻辑 ID 不是硬绑定，网关会按任务、负载、档位改派。

档位对应关系大致是：

UI 档位内部枚举本次观察
Standard（日常任务，快速响应）L0DeepSeek-V4.1-Flash
Turbo（较复杂任务，平衡速度与质量）L1未抓到
Ultra（专业复杂任务，深度推理）L2未抓到

L0/L1/L2 是代码里确认的枚举；UI 与枚举的对应关系是从档位语义推断的，不是官方文档写死的。L0 明显走的是便宜、低延迟的路线；L1/L2 应该会切到更强的模型，但这次没有实测。

为什么没看到文心？本次样本里没有抓到 ernie 或「文心」的实跑模型头。这不等于百度不用文心，而是：客户端把模型抽象成 model-text/model-mm，不暴露厂牌；当前 L0 会话恰好走了 DeepSeek；官方预置列表可滚动，截图只露出两条。

更准确的结论是：DuMate 是一个多模型聚合网关；在这个版本的可观测路径里，百度自研模型只是候选之一。当前可观测到的主力是 GLM、Kimi、DeepSeek、Qwen。

企业版还支持 BYOM：管理员可以接 OpenAI Chat Completions 格式的自建模型，要求上下文和最大输出都不小于 128K，可开启图像理解，按部门控制可见范围。也就是说，模型层不仅能换，还能被企业接管。

九、一次任务的旅程

User → Electron → main-server → router ─┬→ local rules
                                        ├→ meta-harness /routing/decide
                                        └→ Qwen3.5 fallback
                                  ↓
                            OpenCode loop
                                  ↓
                    local proxy → dumate gateway
                                  ↓
                    DeepSeek / GLM / Kimi / Qwen
                                  ↓
                    tools + sandbox + browser + BOS
  1. 用户输入 → Electron 渲染层 → dumate-main-server。
  2. 本地规则 + 远端 meta-harness + Qwen3.5 路由 → 决定任务类型、模型类型、平台、档位。
  3. OpenCode 组装系统提示词（AGENTS/SOUL/USER/MEMORY）、技能、工具、MCP。
  4. 本地代理补鉴权/配额/会话头 → dumate-svc.baidu.com/gateway/apis/v1/chat/completions。
  5. 网关选后端，SSE 流式返回；响应头带真实模型。
  6. 工具进轻沙箱/VM；浏览器走 IAB/CDP；文件走本地/BOS。
  7. 记忆写入 memory.db；遥测、配额、OpenTelemetry 上报。

十、设计取舍：DuMate 到底做对了什么

拆完之后，我觉得 DuMate 最值得学的不是某个模型，而是几个工程选择。

  1. 模型路由是产品能力，不是实现细节。逻辑 ID + 网关 + 真实模型回显，让换模型、分档位、做企业 BYOM 都变成配置问题，而不是重写客户端。
  2. Harness 工程决定下限。官方说通过 Harness 引擎优化，同等任务 Token 消耗降低 75%。这背后是上下文管理、工具编排、失败恢复、沙箱调度，不是换一个更大的模型。
  3. 端云协同是差异点。本地文件、桌面软件、浏览器、语音/图像处理放本地；复杂推理、检索、跨应用编排放云端。纯云端 Agent 很难做到「改我桌面上这个文件」。
  4. 生态兼容降低冷启动。复用 Claude Code 的插件/技能约定，再加上 MCP，第三方能力可以低成本迁入。
  5. 可观测性。X-Dumate-Gw-Realmodel 这种响应头看起来是个小设计，但它让路由可调试、可解释，也方便做用户沟通。

如果我们要做一个类似的 Agent 产品，我会优先抄这三件事：逻辑模型层、沙箱执行层、真实模型回显。

十一、未解的问题

  • L1/L2 的真实模型没有抓到；Turbo/Ultra 到底切到谁，需要再抓一次。
  • 本次没有观察到 ERNIE/文心的实跑头；官方预置列表可能还有更多条目。
  • model-gui-use 的具体厂牌没有在客户端暴露。
  • 版本迭代很快，端口、别名、模型都可能变；本文只代表 v1.0.88。
  • 企业版的私有化/专属部署形态没有覆盖。

如果你也在拆 DuMate，欢迎交流。下一步我打算抓一次 Turbo/Ultra 的网关响应头，把 L1/L2 的模型映射补全。
